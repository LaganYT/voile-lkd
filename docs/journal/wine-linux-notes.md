Convention : MESURE = observé ici, LU = lu dans le code, INFERE = déduit.

## M1 construction (atteint)
- MESURE : outils natifs macOS (widl, wrc, winebuild...) construits dans build-tools (`make __tooldeps__`), bison 3.8.2 de /opt/homebrew/opt/bison (déjà installé, pas de brew install). Journaux logs/wine-linux-tools-*.

## M3 comportements qui dépendent de la page de 4 Kio (LU sauf mention)
Constat principal (LU) : ce Wine CrossOver contient déjà tout le code « page hôte plus grande que la page Windows » (113 usages de host_page_size/host_page_mask dans virtual.c, écrit pour arm64 à 16 Kio) : protections calculées comme l'union des pages de 4 Kio d'une page hôte (get_host_page_vprot, mprotect_range), pages de garde et piles alignées sur la page hôte, vues de fichier qui retombent sur read() quand l'alignement hôte manque, libération et décommit au grain hôte. Sur x86-64 il était figé à 4 Kio. Correctif : host_page_size devient variable sur x86-64 Linux, valeur sysconf (4 Kio, comportement inchangé) ou WINE_HOST_PAGE_SIZE=16384 (même variable lue par wineserver). Construit, non mesuré à cause de wine-2. Décision par comportement :
1. KUSER_SHARED_DATA MAP_SHARED 4 Kio à 0x7ffe0000 : corrigé dans Wine (bloc 64 Kio réservé, pointeur dispatcher à 0x7ffe4000). MESURE : plus d'EINVAL mm.
2. PAGE_GUARD et PAGE_NOACCESS voisins d'une page accessible dans la même page hôte (garde de pile de thread, pile qui grandit, VirtualProtect PAGE_GUARD des applications) : ne fautent pas en matériel. Wine : avec WINE_HOST_PAGE_SIZE=16384 les gardes de pile de Wine sont posées sur une page hôte entière (virtual_alloc_thread_stack, grow_thread_stack). Une garde de 4 Kio posée par une application au milieu d'une page hôte accessible reste invisible : rapport au lead (il faudrait que mm signale l'accès par une autre voie, pas faisable avec l'union matérielle ; INFERE : sans effet pour les piles gérées par Wine).
3. Write watches (MEM_WRITE_WATCH, utilisés par les GC .NET/Mono et certains moteurs) : MESURE userfaultfd ENOSYS, donc Wine prend le chemin mprotect + faute d'écriture, au grain host_page_size. Avec 16 Kio, une écriture marque les quatre pages de 4 Kio (signalement conservateur, correct pour un GC). Fix Wine = WINE_HOST_PAGE_SIZE ; rien à demander à LKD.
4. Vues de section à des décalages de 4 Kio (NtMapViewOfSection, images PE dont RVA et décalage fichier diffèrent modulo 16 Kio) : mm refuse (adresse et décalage doivent avoir la même position dans la page de 16 Kio) ; LU map_file_into_view : EINVAL retombe sur read() pour une vue privée ou en lecture seule. Perte de sémantique seulement pour une vue MAP_SHARED inscriptible mal alignée (mémoire partagée entre processus) : à signaler au lead si un cas réel apparaît.
5. MAP_SHARED de petits objets partagés avec wineserver (session __wine_session, objets partagés de file/fenêtre, mappings de fichiers) : correctif Wine pour la session (64 Kio) ; les autres sections créées par le serveur suivent la granularité 64 Kio des vues Windows (INFERE) ; à mesurer.
6. Pages exécutables et données dans la même page hôte (sections .text/.data d'une image à 4 Kio) : union = RWX en matériel, la détection SMC du moteur gère les écritures (MESURE : messages « SMC write fault » à chaque démarrage, sans erreur). Rien à faire dans Wine.
7. Ordre du sommet de l'espace : `preloader: failed to reserve range 7ffffe000000-7fffffff0000` (MESURE) : l'invité est limité à 0x3fffffff0000 ; Wine s'adapte (host addr space limit). Rien à faire.

## Shaders « argument handle is unknown » : cause trouvée et corrigée
- MESURE (evidence/eac-runs/20261003T002813, journaux de diagnostic des deux côtés) : 18 650 CreateVertex/PixelShader journalisés côté client, les 18 650 décodés côté hôte, aucun en échec ; les ids inconnus (0x4434/0x4435, 0x61d1/0x61d2…) n'ont JAMAIS été créés par CreateVertexShader/CreatePixelShader côté client.
- Cause (LU, code généré du client) : pour un Get à sortie objet (VSGetShader, PSGetShader, OMGetDepthStencilState, RSGetState…, et les emplacements des Get* à tableau), le client place un id invité neuf dans la sortie AVANT l'envoi, puis enveloppe cet id sans savoir si l'hôte a rendu NULL (la réponse ne le dit pas). Quand rien n'est lié, l'hôte rend NULL et n'enregistre rien ; le jeu (sauvegarde/restauration d'état autour d'un passage de rendu, typiquement une incrustation) rappelle ensuite VSSetShader/PSSetShader/OMSetDepthStencilState avec cette enveloppe : « argument handle is unknown », commande abandonnée. Sous Windows, VSGetShader rend NULL et la restauration délie le shader.
- Correctif (renderer, notre copie G/virgl, npt_context.c/.h) : un id invité dont l'objet hôte est NULL est mémorisé (table null_ids) ; une recherche de cet id rend NULL sans échec, donc Set* délie comme sous Windows ; la libération COM de l'id le retire. Les journaux de diagnostic des créations ont été retirés, le journal des Create en échec et celui des enregistrements tardifs restent. Patch : patches/virgl-null-guest-ids.patch.
- Complément : le code hôte généré des 41 répartiteurs Get* (npt_protocol_host_*.h) n'enregistrait la sortie que si elle était non NULL (`if (args.X && *args.X)`) ; la table null_ids ne voyait donc rien. Changé en `if (args.X)` dans notre copie (renderer reconstruit, logs/wine-linux-m6-virgl-build-006.log). À vérifier au prochain run (attendu : plus de « unregistered id … type 61/65 »).
